# Intro

## What is a pipeline, and why DryPipe ?

A pipeline can be described as _"a bunch of programs feeding data to one another"_.

It starts simple, and gets messy very fast:

+ programs in a pipeline are often quite diverse and complex: different languages, CLIs, file formats, exotic requirements
+ they run for hours, so each debug cycle takes hours or days
+ volume compounds the mess: over thousands of tasks, hundreds of failures from a handful of causes, buried in thousands of log files

### How DryPipe addresses this

A DryPipe pipeline is a python function that yields tasks as objects that declare how data flows to and from other tasks.
DryPipe runs them, locally or on Slurm, and tracks the state of each one.

+ diverse programs: tasks call bash or python functions, DryPipe assumes nothing about tools or file formats
+ long debug cycles: a failed task restarts at the step that failed,
  and any subset of tasks can be rerun without touching the others
+ many failures, few causes: `analyze-logs` groups failed tasks by cause (error signature),
  each group can be selected and rerun on its own
+ gets out of the way: tasks are plain directories and human editable json files, no opaque state/database, minimal lock-in, see {ref}`section_out_of_the_way`

A pipeline is plain python, not a new language (#section_why_dsl)

### A DryPipe pipeline is mainly a python function

In DryPipe, tasks of a pipeline are generated by a python generator function

```python
def generate_my_tasks(dsl):

    with open("samplesheet.tsv") as f:
        for line in f:
            sample, r1, r2 = line.strip().split("\t")

            trim = dsl.task(
                key=f"trim-{sample}"
            ).inputs(
                r1=r1,
                r2=r2
            ).outputs(
                trimmed_r1=dsl.file(f"{sample}_R1.trimmed.fastq.gz"),
                trimmed_r2=dsl.file(f"{sample}_R2.trimmed.fastq.gz"),
                report=dsl.file(f"{sample}.fastp.html")
            ).calls("""
                #!/usr/bin/env bash
                fastp -i $r1 -I $r2 -o $trimmed_r1 -O $trimmed_r2 --html $report
            """)()

            yield trim

            yield dsl.task(
                key=f"quant-{sample}"
            ).inputs(
                r1=trim.outputs.trimmed_r1,
                r2=trim.outputs.trimmed_r2
            ).outputs(
                quant=dsl.file("quant.sf")
            ).calls("""
                #!/usr/bin/env bash
                salmon quant -i $SALMON_INDEX -l A -1 $r1 -2 $r2 -o $__task_output_dir
            """)()
```

### Task Keys

A Task Key is the unique identity of a task in a pipeline instance (see pipeline vs pipeline instance in [](definitions.md))

Task keys are entirely at the pipeline developer's discretion (see above example).

+ must be unique within a pipeline instance (hard requirement, globally unique keys are a plus but not a hard requirement, they allow merging together pipeline instances)
+ keys determine the directory structure (choice of keys has long term effect). Task keys that carry meaning (on what the tasks do, what output they produce) help in making the directory structure self documenting.


### Convention on directory structure

A pipeline instance lives in a folder $DRYPIPE_PIPELINE_INSTANCE_DIR

Each task gets two dedicated directories: `output/$__task_key` and `.drypipe/$__task_key`

file layout of above pipeline: 

```
$DRYPIPE_PIPELINE_INSTANCE_DIR
├── output                          task outputs (each task gets one)
│   ├── trim-S1
│   │   ├── S1_R1.trimmed.fastq.gz
│   │   ├── S1_R2.trimmed.fastq.gz
│   │   └── S1.fastp.html
│   ├── quant-S1
│   │   └── quant.sf
│   ├── trim-S2
│   │   └── ...
│   └── quant-S2
│       └── ...
└── .drypipe                        control directories (each task gets one)
    ├── trim-S1
    │   ├── state.completed         the task's state
    │   ├── out.log                 stdout and stderr of the task
    │   ├── drypipe.log
    │   ├── steps.sh
    │   └── task-conf.json
    ├── quant-S1
    │   └── ...
    └── ...
```

The minimalist directory structure, should accommodate most pipelines, pipelines that can't fit into this structure are probably not a good candidate for DryPipe.

## A tool that gets out of the way

DryPipe keeps its state in plain directories and files, so you can inspect and fix a pipeline with `ls`, `cat`, `grep`,
see {ref}`section_out_of_the_way`.

## The task universe

The tasks of a pipeline instance are decided in two layers:

| layer             | how                                        | lifetime              | sees task state ?                  |
|-------------------|--------------------------------------------|-----------------------|------------------------------------|
| 1. generator      | `if`s and conditional yields in code       | the pipeline's code   | yes, it can read task outputs      |
| 2. selection      | `--where-*` options                        | one shell CLI command | yes                                |

Layer 1 defines the **task universe**, layer 2 picks from it the tasks a command acts on.

For work phases that last hours or days, a mask hides tasks from all commands until they are unmasked.

See [](running-pipelines/selecting-tasks.md).

### Growing task universe

The DAG generator is invoked repeatedly during the execution of a pipeline.

The generator can look at the outputs of completed tasks to decide which downstream tasks to yield,
the universe grows as the pipeline progresses. See {ref}`section_dynamic_pipelines`.

A selection only sees the tasks yielded so far, or with `--fs-generator`, the tasks already created on disk:
a `--where-key` matching downstream tasks that are not yet yielded selects nothing.
